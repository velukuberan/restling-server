# Restling Server — Technical Requirements

**Status:** Initial baseline  
**Repository:** `velukuberan/restling-server`  
**Last reviewed:** 2026-11-04

## 1. Purpose

Restling Server is the backend for Restling, an API-client application. Its initial deployment model is a **centrally hosted, multi-user service**. The server will provide the APIs and persistent storage needed for user accounts and, as those capabilities are implemented, projects, collections, environments, permissions, and synchronization.

This document records **technical requirements and selected technologies**. It does not define the source-code directory structure, detailed module boundaries, authorization matrix, database schema, or full API contract. Those belong in the relevant architecture and feature specifications.

## 2. Engineering Principles

- Build modular, cohesive, maintainable components with clearly defined responsibilities.
- Prefer readable and explicit code over clever or terse implementations.
- Keep dependencies intentional and avoid unnecessary coupling between concerns.
- Implement current, demonstrable needs; do not create speculative abstractions, compatibility layers, or infrastructure for hypothetical future requirements.
- Do not change production design solely to accommodate tests or mocking tools.
- Keep infrastructure choices proportionate to the project's present scale and requirements.
- Revisit architectural and performance decisions when evidence justifies doing so, rather than pre-optimizing.

## 4. Execution and Concurrency Model

- **The initial server implementation is synchronous for database access.** Use SQLAlchemy `Session` and `sessionmaker`, not `AsyncSession` or `async_sessionmaker`.
- Database-backed FastAPI handlers should use ordinary `def` where they perform blocking synchronous I/O. Do not run blocking database calls directly on the event loop in an `async def` handler.
- Synchronous execution does **not** imply single-request execution: deployment workers and FastAPI's thread-pool handling of synchronous endpoints can serve concurrent requests.
- Database sessions must not be shared across concurrently executing requests or threads.
- Session creation, cleanup, and transaction ownership must be explicit and consistently implemented.
- Keep transactions appropriately short; avoid holding database locks or connections across unrelated slow operations.
- Use connection pooling with limits appropriate to deployment capacity and measured usage; do not assume unlimited connections.
- **No speculative async migration layer is required.** A future transition to async, if ever warranted, may involve refactoring or rewriting the affected components.

## 5. Persistence and Schema Management

- PostgreSQL is the primary persistent store for the hosted server.
- Use SQLAlchemy 2.x APIs and typed ORM declarations, including `Mapped` and `mapped_column`, for new ORM models.
- Use Alembic for all production schema changes. Do not use ad hoc runtime table creation as the production migration strategy.
- Review autogenerated Alembic revisions before committing them; confirm constraints, indexes, data migrations, and destructive operations.
- Treat migrations as a controlled deployment activity, not an action automatically executed independently by every web worker.
- Define transaction boundaries for operations that modify multiple related records; ensure failure produces consistent rollback behavior.
- Apply database constraints where needed to protect integrity, including uniqueness and referential integrity.
- Never concatenate untrusted input into SQL. Use SQLAlchemy's parameter binding and safe query APIs.
- Test migration application and important persistence behaviors against PostgreSQL.

## 6. Server Responsibilities and Initial Functional Scope

The server's planned capability areas are:

- **User accounts:** Account management and authentication.
- **Authorization:** Enforce access according to resource ownership and permissions.
- **Projects and collections:** Persist and serve user-accessible API-client resources.
- **Environments:** Persist environment data and enforce its visibility and scope.
- **Synchronization:** Support exchanging persistent Restling state between authorized clients and the hosted service.

These areas describe the intended product scope, **not an approved database schema or finalized API design**. Specific roles, authentication mechanisms, synchronization/conflict rules, and environment resolution semantics require separate design decisions before implementation.

The initial implementation should proceed incrementally, beginning with the capabilities selected for the first milestone. A capability listed here is not automatically a requirement to implement it in the first release.

## 7. HTTP API Requirements

- Expose functionality through FastAPI HTTP endpoints using explicit request validation and response models where appropriate.
- Return meaningful HTTP status codes and predictable, structured error responses.
- Keep API behavior consistent across endpoints, including input validation and error handling.
- Document public API behavior through the OpenAPI schema generated by FastAPI, supplemented where behavior is not self-evident.
- Define API versioning and compatibility rules before introducing breaking externally consumed contracts.
- Never expose raw internal exceptions, stack traces, database errors, secrets, or credentials in API responses.
- Enforce authentication and authorization on protected operations, including individual-resource access—not only route-level authentication.

Detailed endpoint names, payload formats, pagination rules, idempotency rules, and version identifiers are **not yet finalized**.

## 8. Security Requirements

- Enforce server-side authentication and authorization for protected resources.
- Treat all client-provided data as untrusted; validate it at the HTTP boundary and enforce business invariants within the appropriate application logic.
- Enforce account/resource ownership and access permissions on every relevant data operation.
- Store passwords only using a suitable modern password-hashing scheme; never store plaintext or reversibly encrypted passwords.
- Manage secrets through configuration or secret-management facilities, never hardcode them or commit them to source control.
- Use TLS for externally exposed production HTTP traffic.
- Avoid logging passwords, access tokens, API keys, environment secrets, or sensitive request/response payloads.
- Use parameterized database operations and least-privilege database credentials.
- Establish rate limiting and abuse protection for sensitive endpoints as part of their feature design.
- Review threat-sensitive changes—including authentication, authorization, secret storage, and synchronization—with appropriate tests.

Specific identity flows, token/session formats, password-hashing library, and secret-encryption design remain open decisions.

## 9. Configuration and Deployment

- The primary deployment target is a **centrally hosted, multi-user service**.
- Separate local, test, and production configuration without hardcoded environment-specific credentials.
- Keep operational configuration explicit and documented, including database connection settings and connection-pool limits.
- Support clean application startup and shutdown, and provide basic health/readiness capabilities appropriate to the deployment.
- Ensure database migrations can be applied before deploying application code that depends on them.
- Record production failures and operationally useful events without exposing secrets or unnecessarily sensitive data.
- Deployment topology, hosting provider, process/worker count, containerization, and monitoring stack are not yet prescribed by this document.

A future self-hosted distribution or alternative server implementation is **not** assumed by this initial hosted deployment baseline. If such support becomes a committed requirement, its compatibility and protocol obligations must be specified separately.

## 10. Code Quality and Testing Requirements

- Ruff is the canonical formatter and linter; Pyright is the canonical static type checker.
- Prefer fully annotated production function signatures and modern Python typing conventions.
- Target strict Pyright checking, allowing narrowly justified exceptions for genuine dependency or typing limitations.
- Tests must be deterministic, independently runnable, and named by observable behavior.
- Cover successful behavior, important failures, edge cases, and security-sensitive access boundaries.
- Keep most business-logic tests fast; use integration tests for real persistence, HTTP contracts, and external boundaries.
- Test SQLAlchemy transactions and migration behavior against PostgreSQL where correctness depends on database behavior.
- Do not reshape production classes solely to satisfy a mock library. Use real collaborators where practical; mock genuine external systems or infrastructure boundaries.
- Run linting, formatting checks, type checking, and appropriate tests in CI before merging changes.

Recommended baseline checks:

```bash
uv lock --check
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

The concrete commands may be consolidated in a Makefile or equivalent workflow without changing their responsibilities. Detailed coding conventions and test organization belong in `CODING_STANDARDS.md`.

## 11. Documentation and Change Control

Project documents have these distinct purposes:

1. `ARCHITECTURE.md` — modules, responsibilities, dependency direction, boundaries, and architectural decisions.
2. `TECHNICAL_REQUIREMENTS.md` — selected stack, technical constraints, and required capabilities.
3. `CODING_STANDARDS.md` — code style, implementation discipline, test conventions, and enforcement.
4. `README.md` — project overview, setup, and routine developer commands.

When these documents conflict, follow the order above and explicitly resolve the inconsistency.

Changes to the runtime baseline, primary database, ORM, execution model, or deployment model require an explicit decision and corresponding documentation update. Do not silently substitute technologies or change public contracts.

## 12. Deliberately Undecided

The following are **not** fixed by this document and must not be inferred as already approved:

- Exact source-code package/directory layout and layering.
- Authentication protocol, account verification and recovery, and token/session design.
- Detailed authorization roles, permissions, ownership rules, and sharing behavior.
- Project/collection/environment data model, inheritance, precedence, and secret-handling semantics.
- Synchronization protocol, versioning, conflict resolution, and offline behavior.
- API endpoint paths, request/response schemas, public contract version, and pagination strategy.
- Database pool sizes, worker counts, deployment infrastructure, and operational SLOs.
- Specific ancillary packages for hashing, HTTP integration testing, background work, and observability.

Decide these through focused design discussions and record the resulting decisions in the appropriate documents before implementing dependent features.
